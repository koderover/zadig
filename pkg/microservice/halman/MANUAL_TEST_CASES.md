# AI 助手手动测试用例

## 测试范围

本轮只执行以下 **15 个核心场景**，覆盖六个内置 Skill 和主要业务保护。末尾 P2 为可选专项验证，不计入本轮用例数。

模型措辞无需逐字一致，任务目标、参数、实际操作、权限和最终状态必须一致。所有用例均待手动执行，不代表已经通过真实环境验证。

## 测试准备

- Halman 单实例运行，表结构与当前版本一致；AI 助手已开启，模型支持工具调用。巡检和效能诊断所需的原功能模型也已配置。
- 准备管理员、有目标项目查看及构建创建权限但无服务创建权限的账号，以及无目标资源权限的账号。效能诊断和 AI 助手报告权限分别准备。
- K8s YAML 项目 `aiceshi` 中已有 `service1`、`service2`、`service3`，各自有唯一构建组件；另备一个多组件服务。
- 已有构建模板 `general`；代码源别名 `gitlab`，组织 `kr-poc`，仓库 `multi-service-demo`，分支 `main`。参数与实际环境不符时统一替换。
- 准备可导入的 YAML 和 Helm 配置、服务模板及必填变量；一条失败的工作流任务、异常测试服务、可重启/回滚的测试环境，以及有近期效能数据的项目。
- 开始前记录目标项目的服务、构建、环境和工作流列表，以及报告指标。每次创建使用未占用的名称，避免测试残留影响结果。

涉及创建、重启和回滚的步骤只对专用测试资源执行。请求、日志和截图须隐藏 Authorization、Cookie、Token 及仓库/模型凭据。

## 执行与取证

界面未接入的功能可使用 Swagger 或 HTTP 客户端。每个场景记录会话 ID、内部运行 ID、Skill 根执行 ID 和实际结果；用 Zadig 原功能页面核对资源，不能只看模型说“完成”。

### 补问请求约定

`POST /api/halman/conversations/{conversation_id}/runs` 使用 AG-UI 请求体。路径会话 ID 与 `threadId` 一致；每轮新问题使用新的 `runId` 和消息 `id`。补问必须传入上一轮返回的 `skill_execution_id`，不能用当前 `runId` 替代。

```json
{
  "threadId": "原会话ID",
  "runId": "manual-build-002",
  "messages": [
    {
      "id": "manual-message-002",
      "role": "user",
      "content": "共用同一份，代码源 gitlab，组织 kr-poc，代码库 multi-service-demo，分支 main。"
    }
  ],
  "forwardedProps": {
    "skill_execution_id": "上一轮返回的Skill根执行ID",
    "page_context": {
      "page_type": "service",
      "project_key": "aiceshi",
      "service_name": "service1"
    }
  }
}
```

首次请求可省略 `skill_execution_id`。从 `STATE_SNAPSHOT` 取得内部运行 ID，再通过 `GET /api/halman/runs/{id}` 核对草稿、清单和状态。`RUN_FINISHED` 只代表本轮流结束，不代表业务已完成。

## 15 个核心场景

### 01. 已有三个服务批量创建构建（本次重点回归）

**步骤**

1. 输入：“在 aiceshi 项目中使用 general 构建模板，为 service1、service2、service3 创建构建，先给出清单。”
2. 按上述约定关联原任务，回答：“共用同一份，代码源 gitlab，组织 kr-poc，代码库 multi-service-demo，分支 main。”
3. 补齐实际缺少的构建名称、模板变量，核对清单后确认。
4. 使用只有构建创建权限、无服务创建权限的账号，换新构建名再验证一次。

**预期**

- 不要求已有服务的 YAML/Chart 来源，不查询服务配置路径，不要求创建环境。
- 正确解析 general 的真实模板 ID；代码源查询使用 `/api/code/codehost`，仓库查询包含 `repoOwner=kr-poc`，不能只传完整路径关键词。
- 共享源码参数应用于三个构建，唯一组件自动读取。清单恰好三个 `create_build`，没有服务、环境或工作流创建动作。
- 确认前无新增资源；确认后构建的模板、源码和组件绑定正确，不覆盖服务、不自动运行构建。无服务创建权限不妨碍仅创建构建。

### 02. 构建目标异常

**步骤**：分别请求为不存在的服务、多组件服务创建构建；再测试未选择构建模板和构建名称已存在。

**预期**：服务不存在时明确说明；多组件时让用户选择真实组件；无已有模板不创建构建；同名构建不覆盖。不能生成悬空绑定、擅自创建服务，或把空操作清单计为成功。

### 03. 多轮补问与页面切换

**步骤**：开始一个三服务任务，分轮补参数；只修改第二个服务或构建的参数；切换到另一项目页面后，仍关联原根执行 ID 继续。另做一次故意漏传根 ID 的对照。

**预期**：已有参数及其他两个对象不丢失，原项目不被新页面覆盖，会话不切换。缺少关联时明确提示恢复任务或重新提供目标，不能根据页面擅自开始另一项初始化。记录请求体以区分调用端漏参与后端问题。

### 04. K8s YAML 项目初始化

**步骤**：只输入“帮我初始化一个 K8s YAML 项目”；随后分轮提供项目名称、三个服务名、已有 YAML 来源及文件分组。生成清单后确认。

**预期**：先保存草稿、补问真实缺项；保留用户指定的三个服务和总数。项目默认私有，当前用户包含在管理员中；配置来源和分组正确。只有源码、无 YAML/Chart 时说明条件不足，不 clone、不写仓库、不生成配置冒充导入成功。

### 05. 已有项目批量添加服务及 Helm 初始化

**步骤**：向已有 K8s 项目批量添加服务，使用服务模板并补齐必填变量；再向 Helm 项目导入已有 Chart，指定真实来源和具体版本。核对清单后确认。

**预期**：模板按名称解析，缺变量时只问缺项；拒绝同名覆盖、项目类型不匹配和无效 Chart 版本。新服务同时创建构建时，构建依赖对应服务成功；已有服务仅创建构建不需要此依赖。未经请求不附加环境或工作流；需要工作流时复用 `AutoCreateWorkflow`。

注意：原有服务导入可能受平台自动部署配置影响，应核对实际副作用，不能仅凭未添加环境动作就认定不会部署。

### 06. 确认清单保护与失败重试

**步骤**

1. 生成清单后，仅在聊天输入“确认”，再使用卡片明确拒绝。
2. 重新生成清单，修改参数后尝试批准旧版本；另测试生成后修改模板。
3. 批准有效清单，并重复发送同一确认请求。
4. 制造一个动作失败，使用重试入口生成新清单并确认。

**预期**：聊天不能替代确认；拒绝、过期、旧版本和模板已变化的清单不能执行。重复确认不重复写入；重试不重做成功项，仍需明确确认。结果未知时先只读核实，不直接重放。

### 07. 工作流报错分析

**步骤**：在失败工作流任务页输入“帮我检查工作流报错怎么回事”；再分析当前配置已变更的旧任务，以及日志不可用的任务。

**预期**：使用正确项目、工作流和任务，结合当次状态、失败步骤及有限日志给出证据和建议；不把当前配置冒充当次配置，不泄露凭据。证据不足说明缺口，不编造根因，不自动重跑或改配置。

### 08. 服务报错分析与确认修复

**步骤**：在异常服务页面请求分析，随后明确请求重启或回滚，核对清单及目标版本后确认。

**预期**：诊断验证环境和服务归属，结合状态、有限日志和事件；仅分析时不写入。修复必须通过确认流程，执行后核对实际结果；诊断成功不能代替修复成功，未知结果不能报告已修复。

### 09. 环境巡检与历史

**步骤**：输入“巡检一下 aiceshi 的 dev 环境健康状态”；再查询最近五条历史。对照测试未配置巡检项/模型或返回空报告的情况，以及生产和测试同名环境。

**预期**：复用原报告并注明目标、时间和来源，不把历史当当前状态。生产属性和环境隔离；空报告、失败或缺配置不能描述为健康，也不计完成。不发定时通知、不自动修复，不因失败自动重复调用原模型。

### 10. 效能诊断

**步骤**：输入“分析 aiceshi 项目近一个月的质量和效率，并给出优化建议”；使用有效能洞察权限但无项目权限的账号验证，再用仅有项目权限的账号对照。另测试同名项目及超过十个项目/九十天。

**预期**：仅分析明确指定项目，默认最近三十天，显式范围生效；只使用原报告 answer，不输出内部提示词。按效能洞察权限授权；项目歧义补问，超范围要求缩小，不扫描所有项目。

### 11. 登录、资源权限与 AI 开关

**步骤**：使用失效/撤销 Token、无资源权限账号和他人会话 ID 测试；完成诊断后撤销资源权限，再查看历史、补问和重新回答。关闭 AI 后分别尝试新任务、确认及历史查询。

**预期**：登录/MFA/企业版和归属校验有效，不能越权读写。本人保留期内历史仍可查看，但历史进入模型或重新查询须重验权限。关闭 AI 阻止新任务及确认，不删除历史；已提交业务不能承诺撤回。

### 12. Skill 管理和推荐

**步骤**：管理员查看六个 Skill，追加规则、停用再恢复默认，重启后查询；非管理员尝试修改。停用前保留一个合法补问任务，停用后分别继续旧任务和发起新任务。

**预期**：正文只读，启停及追加规则持久化；非管理员修改被拒绝，未知 ID/额外字段/超过 8000 字节规则被拒绝。停用禁止新任务并过滤推荐，合法旧任务可继续；推荐最多三项且不重复。追加规则不能扩权或跳过确认，运行中快照不变，后续生成读取新规则。

### 13. 系统语言和模型配置

**步骤**：分别使用中文、英文系统配置测试回答、补问、标题、推荐、Skill 展示及可见推理；切换助手模型后发新问题。英文系统下触发 AI 代码审查，再切回中文查看已有评论。

**预期**：新请求遵循系统语言和所选模型，历史保持原文；可见推理不遵循语言时记录模型表现缺陷。代码审查由创建任务时的系统语言驱动，已有评论使用报告语言。巡检/效能原模型与助手模型分别生效，不静默混用。

### 14. 报告统计与导航

**步骤**：记录初始指标，完成普通聊天、多轮补问、三服务任务和失败任务；切换两个模型各运行一次。查询 overview、trends、skills、rankings，并用报告授权账号和未授权账号访问。

**预期**：普通聊天、补问及待确认不计完成；三服务任务按根执行只计一次，重试/重新回答不重复计同一目标。概览含等长上期和系统总用户数；Token 按模型展示，原报告估算不混入实际用量；分类固定四类且用户去重，排名含用户名。报告权限独立校验，默认导航按各自权限展示 AI 助手报告和 AI 审查分析。

### 15. 会话恢复、幂等、取消和删除

**步骤**：原样重发同一 runId；SSE 中途断开后重订阅同一运行；刷新历史；生成时取消，再删除空闲会话。对照测试修改正文却沿用 runId，以及删除活动运行会话。

**预期**：同一请求不重复调用模型或执行写入；冲突请求拒绝。断线不取消后台任务，重订阅不启动新任务；历史可恢复。取消停止未提交操作，但不保证撤回已提交业务；活动或仍待核实的会话不可直接删除，空闲会话删除后不可再读取。

## P2：可选专项验证（不计入以上 15 个场景）

只在隔离环境执行，不作为本轮普通手测的前置条件。

| 专项 | 操作 | 检查重点 |
| --- | --- | --- |
| 进程恢复 | 模型运行中重启；另在业务已提交但结果未保存时重启 | 普通运行恢复为中断，写结果未知时待核实；不自动重放，不伪造完成数和 Token |
| MySQL 故障 | 受控模拟结果保存失败，再恢复数据库 | 不显示保存成功；错误可定位且无敏感数据；恢复后无重复统计贡献 |
| 并发与连接 | 调低活动并发，用不同账号同时提交 | 满载短等待后友好提示，不建设业务队列；拒绝请求不建运行、不调用模型；连接不超过配置预算 |
| 保留策略 | 用受控到期数据验证默认九十天及调整后的清理 | 到期聊天及依赖数据清理后不可继续引用；Skill 不随聊天删除，日聚合按独立策略保留 |
